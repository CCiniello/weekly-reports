01Broken pages (4xx / 5xx)5,835 URLsError
Why it matters

Every broken URL is a dead end. Google only spends so much attention crawling our site, and thousands of dead ends burn that budget instead of landing on the pages we want ranked. It's the single biggest reason our score is 36.

What these actually are: each one is a whole URL — a complete web address — that returns an error instead of a page. (A "4xx" is always the entire address, never "part of a page" — you can't half-break a page this way.) Two kinds: 404 = "not found" (address doesn't exist) and 403 = "forbidden" (server refuses it). The 5,835 figure counts broken sub-resources too; the core internal broken pages are 731 (+9 this week), of which 420 are hard 404s (+5). Server errors (5xx) are nearly gone — down to 1 from 6. They sort into the three named causes in cards 02–04.

Likely why: leftover URLs from the WordPress→Astro migration that were never redirected, plus the three root causes below. Most of this number collapses once cards 02–04 are fixed.

The fix — step by step
  1. Fix the three root causes below first (staging copy, email bug, localized 403s) — they're the large majority.
  2. Re-crawl, then export whatever 4xx URLs remain.
  3. For each remaining one: if a live equivalent exists, 301 to it; if it's gone for good, return 410 so Google stops retrying.
  4. Remove internal links that still point at dead URLs.

03The support-email link bug is manufacturing broken URLssitewideRoot cause
Why it matters

A single one-line coding mistake is generating fake broken pages on every page of the site — inflating our error count for no reason. Tiny fix, disproportionately large cleanup. This task is now overdue (was due Jul 25).

What this actually is: the support email is written as a normal link (href="support@revealbi.io") instead of an email link (href="mailto:support@revealbi.io"). Missing the mailto:, the browser and Google read it as a page and try to visit revealbi.io/support@revealbi.io — which doesn't exist, so it errors (403). It's in the footer/contact area of nearly every page, so it multiplies fast.

See real example URLs
  • https://www.revealbi.io/support@revealbi.io 403
  • https://www.revealbi.io/glossary/support@revealbi.io 403

Same email, rendered as a path on many pages → many broken URLs. Confirmed present in Jul 22 crawl.

Likely why: a template/component where the email was pasted as a link without the mailto: prefix.

The fix — step by step
  1. Find where the support email is output (footer or contact component).
  2. Change href="support@revealbi.io" to href="mailto:support@revealbi.io" — or show it as plain text.
  3. Search the codebase for other bare email-as-link instances; fix the same way.
  4. Redeploy and re-crawl.

05Canonical tags pointing at broken / redirecting URLs384 URLsError
Why it matters

A canonical tag is a page telling Google "this is the official version of me." On 384 pages that pointer aims at a dead, moved, or redirecting URL — so we're telling Google the real version of these pages is broken, and Google may drop them from search.

What this actually is: 380 pages have a canonical pointing at a broken (4xx) URL (+5 this week), 3 now point at a redirect (brand-new this week — was 0), and 1 points at a server error (down from 3). Think of it as a page handing Google a forwarding address that leads nowhere.

Likely why: the canonical logic still builds URLs in the old pre-migration structure.

The fix — step by step
  1. Export the affected URLs (Page Explorer → "Canonical points to 4XX" / "…to redirect").
  2. Find where canonicals are generated (Astro layout / SEO component).
  3. Make each page's canonical point to its own final, live (200) address (self-referencing for standard pages).
  4. Spot-check 5–10 rendered pages after deploy; re-crawl.

07Internal links pointing at redirects1,833 pagesWarning · rising
Why it matters

Not fatal, but it's death by a thousand cuts — and trending the wrong way (+184 this week, the biggest upward mover). Every link that goes through a redirect instead of straight to the final page wastes crawl budget and leaks a little ranking value.

What this actually is: 1,833 indexable pages contain internal links that point at an old URL which then bounces (redirects) to the real one, instead of linking to the real one directly. Counting non-indexable pages too, it's 4,642 pages (+185). It's the clearest rising trend in this crawl.

Likely why: old internal links never updated to the new URL structure after the migration.

The fix — step by step
  1. Export the redirect map (old URL → final URL) from the migration/server config.
  2. In templates and shared components (nav, footer, CTAs), swap old URLs for their final destinations.
  3. Bulk find-and-replace in-content links across the CMS using the map.
  4. Redeploy; re-crawl to confirm the count drops.

6 Cheat sheetevery term above, in plain English

Health score
Ahrefs' rough 0–100 grade for the site's technical shape. Directional, not precise — a low score means lots of errors on the pages it crawled. Watch the trend.move it up over time
4xx vs 5xx (broken pages) — and "is it the whole page?"
A 4xx/5xx is always the whole URL (the whole address), never part of a page — you can't 404 half a page. 404 = not found. 403 = forbidden (server refuses access). 5xx = server failed to deliver it. All are dead ends that waste Google's crawl attention.fix: web dev
Canonical tag
A hidden tag telling Google "this is the official version of this page," used when similar pages exist. If it points at a broken or redirecting URL, you're telling Google the real version is dead/moved — so Google may drop the page.fix: web dev
Noindex / nofollow
Noindex = "do not put this in search results." Nofollow = "don't pass ranking credit through this page's links." Fine when intentional; harmful when it hits pages we want found.fix: web dev / CMS
XML sitemap
The clean list of URLs we hand Google saying "these are my real pages." It should contain only live, canonical, indexable pages — never broken or redirecting ones.fix: web dev
Redirect (3xx) & redirect chain
A redirect forwards one URL to another (used when a URL changes). Normal in small numbers. A chain is A→B→C — several hops — which is slow and leaks a little value each hop. Link straight to the final URL.fix: web dev
Crawl budget
The finite attention Google spends crawling our site. Every dead end, redirect, and junk URL eats into it — so broken pages literally cost our good pages visibility. The "why it matters" behind most of this report.the core idea
Non-production subdomain (staging / dev / old)
A test/pre-launch copy of the site (wp-staging., dev., old.). Should never be reachable by Google — if it is, it competes with the real site as duplicate content.fix: web dev / infra
mailto: link
The correct way to code an email as a clickable link (mailto:name@site.com). Without mailto:, the browser treats it as a page on your site — the bug in card 03.fix: web dev
